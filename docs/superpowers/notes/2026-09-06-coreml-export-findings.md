# Core ML export findings

**Date:** 2026-09-06
**Task:** Milestone 1, Phase A, Task 4 — the decision gate

## Decision

**Keep YOLO. Export with `nms=True`.** Do not retrain a semantic segmentation
model at this stage.

## Why

The concern going in was that YOLO-seg exports as raw tensors and would need
several hundred lines of Swift plumbing — anchor decode, NMS, coefficient
gather, prototype matmul, sigmoid, crop, threshold, upsample — none of which is
related to the project's actual contribution. Against that, a single-class
semantic segmentation model exports image-in → mask-out with no decoding at
all, and the pipeline only ever uses the largest mask, so nothing of value
would be lost by switching.

Passing `nms=True` to the export removes most of that plumbing. Ultralytics
bakes non-maximum suppression into the Core ML graph, so the detection output
arrives already resolved.

| Export | Detection output | What Swift must do |
|---|---|---|
| `nms=False` | `[1, 37, 8400]` | Decode 8,400 anchors, threshold, run NMS, then everything below |
| `nms=True` | `[1, 300, 38]` | Pick a detection, then everything below |

That drops the hard, fiddly half. What remains is mechanical: take the chosen
detection's 32 mask coefficients, matrix-multiply against the `[1, 32, 160,
160]` prototypes, sigmoid, crop to the box, threshold, and upsample into frame
space. The matmul is 32 × 25,600 multiply-accumulates, which `vDSP` does
without breaking a sweat.

Estimated Swift decoder: roughly 100 lines, against roughly 250 for the
`nms=False` path.

Retraining stays available, and nothing in the design forecloses it — the
pipeline's entire contract with the model is one binary mask. See the design
spec on the `PavementSegmenter` seam.

## The exported contract

`train11-yolov8n-seg-640.mlpackage`, fp16, 6.5MB, Core ML spec version 6.

```
INPUT
  image        640x640 RGB

OUTPUT
  var_1157     [1, 300, 38]        NMS-resolved detections
                                   38 = 4 box + 1 conf + 1 class + 32 mask coefficients
  var_960      [1, 32, 160, 160]   mask prototypes
```

Output tensor *names* are generated by the converter and change between
exports. Swift must bind by index or by shape, never by name.

## Export fidelity

`model/tests/test_coreml_parity.py` compares the largest mask from the Core ML
export against the PyTorch checkpoint, over eight frames from the v1 test split.

| image_0142 | 0.9983 |

`nms=False` exports pass; the numbers above are for `nms=True`.

## Two things found along the way

**Fixture selection was biased.** The plan said to take the first five images
of the sorted test split. Those turned out to all come from one source video —
the split is 65 video frames and 465 standalone stills, and the video frames
sort first. The fixtures are now eight frames spread evenly across the whole
split. All 530 test images carry a non-empty label, so a miss is a real miss
rather than an empty scene.

**Detection reliability on video frames is worse than on stills, and v1's
threshold was hiding it.** On `IMG_7001_mov-10/11/13` the model's best
detection scores 0.31, 0.40 and 0.21 — all below the `conf=0.5` that v1 used in
production. The model is firing on the pavement, but not confidently enough to
survive the threshold.

This is consistent with the checkpoint's mask recall of 0.754, and it means v1
was dropping roughly a quarter of frames outright. Worth investigating properly
at the pathfinding milestone: whether the right answer is a lower threshold,
temporal smoothing across frames, or retraining. Not a blocker for getting the
model on-device, and recorded here so it is not forgotten.
